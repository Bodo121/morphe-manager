# SakuraPatcher release signing

The automated GitHub Actions workflow **Publish SakuraPatcher release** now builds the optimized **release** variant, verifies APK signatures and `app.morphe.manager` package identity, and publishes a versioned GitHub Release. It **never publishes a disposable debug-signed APK**.

## One-time signing-key setup (repository owner)

If you already have a persistent signing key for `app.morphe.manager`, reuse it. **Do not replace an existing release signing key**, or future updates will fail Android signature verification.

Otherwise generate a fresh signing key locally using an installed JDK. Keep the private file and passwords in secure offline backups:

```sh
keytool -genkeypair -v -keystore sakura-release.jks -alias sakura -keyalg RSA -keysize 3072 -validity 10000
```

Choose and securely save the keystore password and key password.

In **GitHub → Bodo121/morphe-manager → Settings → Secrets and variables → Actions**, create the following four **repository secrets**:

- `KEYSTORE_B64`: Base64 of the complete contents of `sakura-release.jks`. On PowerShell: `[Convert]::ToBase64String([IO.File]::ReadAllBytes("C:\\path\\to\\sakura-release.jks"))`. On Linux: `base64 -w0 sakura-release.jks`.
- `KEYSTORE_PASSWORD`: keystore password.
- `KEYSTORE_ENTRY_ALIAS`: `sakura` (or the alias in your existing key).
- `KEYSTORE_ENTRY_PASSWORD`: the key password.

Do **not** commit the .jks file, passwords, or Base64 text to this public repository. Store an offline backup. If you lose the signing key, you generally cannot update existing installations under the same signing identity.

After configuring the secrets, open **Actions → Publish SakuraPatcher release → Run workflow**. The workflow compiles, signs, verifies, uploads an artifact, and creates the release if every step passes.

### APK upgrade and installation details

- The current test installation uses application ID `app.morphe.manager.debug` and launcher label `SakuraPatcher Debug`.
- The production release uses `app.morphe.manager` and launcher label **SakuraPatcher**.
- The release is therefore a **separate app** from the debug installation. It will not automatically overwrite the debug APK or inherit its private app data. Back up profiles/settings if needed, then install the release.
- The actual APK's `versionCode` is generated by the build, while the GitHub Release tag is versioned per workflow run.
- Compilation of release sources is checked **even before signing**; if signing is not configured, the workflow stops safely without publishing an insecure or un-installable APK.
